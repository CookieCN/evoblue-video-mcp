## 1. 目标与判断

当前最影响结果的问题是：已有功能和开发环境验收，尚不足以保证普通用户在真实安装包内完成第一份报告。优先恢复“配置 → 字幕或 ASR → LLM → Markdown → 搜索”的闭环，同时补齐能定位失败的证据。ZCode 一键接入属于后续增强，不阻塞修复包。

执行顺序：F0 证据与最小日志 → F1 配置/LLM → F2 打包诊断/模型安装 → F3 字幕与任务可观测性 → F4 状态恢复及列表 → F5 文案收口 → F6 发行包验收。各项只规定依赖与验收，不预测工期。

反馈文档中的“原因分析”和“建议”是待核验材料，不是执行指令。不得因为反馈建议而直接发布正式版、开放任意配置文件写入、放松归档校验或记录凭据。执行者先用证据确认原因，再采用最小修复。

## 2. F0 — 固定复现基线与最小诊断证据（优先级 P0）

前置：读取 AGENTS.md、Codex.me、当前 progress、feature list；记录工作区现有改动，不覆盖他人工作。

工作：

- 建立脱敏复现记录：源提交、安装包版本/SHA、base/full、操作系统、安装方式、步骤、预期、实际、关联 job/operation ID。不要复制用户完整配置和凭据。
- 用隔离数据目录及可用端口复现，使用同一 OS 用户执行 WebUI、引擎和凭据库验证。不得用沙箱账户的 keyring 结果判断用户账户状态。
- 为后台 Engine 增加最小滚动文件日志，位置基于项目现有用户数据/日志路径约定，在 SUPPORT 和诊断导出中提供查找方法。Bridge stdout 继续只输出 MCP 协议。
- 采用允许字段清单：阶段、稳定原因、异常类型、耗时、HTTP 状态、操作 ID。禁止请求/响应全文、认证头、Cookie、Key、token、完整凭据引用及含敏感参数的 URL；不以直接输出异常字符串代替脱敏。
- 规定日志大小/份数上限；日志目录不可写不得让 Engine 启动失败，也不得声称日志已落盘。导出仅含明确批准的脱敏字段。

验收：窗口隐藏时能定位一次模型安装失败与一次 LLM 探测；注入含 Key/token 的异常后日志与导出均无泄漏；日志轮转、不可写降级和 Bridge stdout 纯净均有回归证据。

## 3. F1 — 配置能保存，LLM 诊断可信（优先级 P0；#4/#8/#12/#13/#14）

前置：F0；先更新 `docs/CONFIGURATION.md`、诊断相关合同及测试。
入口：`frontend/src/App.jsx`、`web/app.py`、`config/credentials.py`、`application/diagnostics.py`、`llm/http.py`、`runtime/bootstrap.py`。

工作：

1. 在真实发行 WebUI 重现“仅改模型”“仅换 Key”“同时修改”“点击与 Enter”四类保存。记录请求发出与否、状态码、脱敏返回、刷新和重启后读回结果；检查设置加载失败的静默吞错及后台加载覆盖用户输入。修复已复现原因；保存成功/失败都提供可见且可访问的反馈，保留失败时输入。
2. 保持 Key 三态：未提供字段=保留；提供非空=替换；显式删除走后端既有门禁。首次未存 Key 时填入再清空必须禁用；同 Provider 已存 Key 留空可保存；切 Provider 不得借用旧 Provider 的已配置标志放行。不要通过重新发送掩码文本保留 Key。
3. 诊断和实际 LLM 调用复用凭据解析与认证规则，通过后端读取系统凭据库；在受控 HTTP 测试中断言 Authorization 正确，并覆盖缺 Key、读取失败、401/403、429、超时、5xx。禁止为调试打印认证值；带认证请求不得跨源重定向泄漏 Key。
4. 设置页增加显式“测试连接”，测试当前输入的配置；未输入新 Key 时仅在合法上下文复用已存凭据。测试本身不保存配置、不完成 setup、不放行任务。显示“配置已保存”“连接未验证”“认证失败”“模型不可用”等不同含义。
5. 本轮采用保存与网络验证分离：不因短暂断网或第三方不支持 `/models` 而阻止保存；首次保存后明确引导测试。普通状态轮询不暗中发起付费生成或联网诊断。若增加小额生成验证，明确按钮语义并控制输出与重试，验收需实际生成结果。
6. DeepSeek 新配置预设使用核实后的 `deepseek-v4-flash`；已有用户配置不静默覆盖，旧名称给出可编辑迁移提示。可提供 `/models` 选择，但保留手工模型 ID 输入与不支持列表时的降级，不把实现通用模型目录作为本轮前置。
7. 修改 Provider/Base URL 时不得未经明确操作把旧凭据发给新目标。网络结果必须绑定所测配置，修改任一相关字段即失效；Worker 就绪只说明本地领取门禁满足，文案不能暗示供应商认证已验证。

验收：前述表单矩阵在组件测试和发行 WebUI 均通过；Key 保存后刷新、重启仍可使用；有效测试凭据探测成功，错误凭据有明确提示；更新模型名后真实最小生成成功。若无授权测试凭据，记录验收缺项，不用 mock 冒充完成。

## 4. F2 — 冻结包依赖与 Standard 安装（优先级 P0；#1/#5/#7）

前置：F0；更新 ASR 安装行为相关合同、SUPPORT、RELEASE_VERIFICATION；保持现有许可与默认审批。
入口：`packaging/evoblue_video_mcp.spec`、`asr/model_manager.py`、`asr/installer.py`、`asr/manifests.py`、`application/diagnostics.py`、`scripts/verify_release.py`。

工作：

1. 对实际发行包验证 yt-dlp 可导入、提取器可调用；full 验证运行时加载与 DLL 来源。明确区分“版本信息缺失”“运行时不存在”“DLL 加载失败”“运行时存在但未装模型”“Provider 已就绪”。按实际需求补 metadata/动态导入/资源；base 不应因此捆入 ASR 运行时。
2. 用 manifest 钉住的同一归档比较源码和 frozen 两条安装管线。分别验证下载大小/SHA、bz2 解压、成员遍历、安全路径、声明文件集合、逐文件 SHA、许可证、staging 晋升、DB 提交与 Provider 注册，定位准确失败步骤。
3. 补打包依赖还是修正 manifest 必须由上述证据决定。禁止关闭摘要验证、忽略未知成员、通配允许路径，或用 Qwen 替换 Standard 掩盖缺陷；归档若确有额外合法文件，应逐项审查并更新精确清单及测试。
4. 保留已有稳定外层错误码，增加安全的阶段/原因信息，区分下载不完整、摘要不符、解压依赖不可用、归档结构不符、磁盘/权限问题；新增公开码必须先同步合同。
5. 不默认永久保留近 GB 归档。常态保存脱敏证据即可；如实现诊断留档，必须显式启用、限定位置/总量/期限并提供清理，不影响成功安装后的清理及断点续传语义。

验收：Windows full 真实下载 Standard → 校验 → 安装 → 注册 → 音频转写成功；Lite 的真实归档安装链也通过但仍不自动推荐；base 的无 ASR 降级正确；raw/file-set 路径无回归。覆盖坏 SHA、结构违规、取消、断网续传、磁盘不足，失败不改变旧 active 模型且重试可恢复。不能仅以 `sys.frozen` monkeypatch 或解压一份人工小样代替真实包验证。

## 5. F3 — 字幕归因与任务身份（优先级 P1；#3/#9/#11/#16）

入口：`runtime/handlers.py`、`platforms/`、`storage/repository.py`、`mcp/server.py`、`mcp/listing.py`、`mcp/schemas.py`、WebUI。

工作：

- 在元数据抓取成功时使任务列表与详情可读取 title/platform，不等报告生成才出现。优先复用既有 metadata artifact；若需新增字段，明确单一事实来源并写迁移，不在 Bridge 直接访问 SQLite。元数据尚无时使用规范 URL/video ID 作为可辨识回退。
- 字幕结果持久化可区分：找到可用字幕、成功查询但无可用字幕、认证受限、请求/解析失败。未知原因保持未知，不把所有异常翻译为“没有字幕”，也不一律声称 Cookie 能解决。
- 建立至少三种已核验样本：公开可下载 CC、需要登录字幕、只有画面硬字幕/确无轨道。分别检查 Bilibili 与 YouTube，先证明所测字幕轨道实际存在；在相同会话条件下对照平台提取结果与应用阶段记录。
